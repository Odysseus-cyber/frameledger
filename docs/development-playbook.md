# FrameLedger 系统开发思维手册

更新日期：2026-11-13。状态：开发与学习方法已确定，工程实现和首个练习尚未完成。

项目同时追求两个成果：**做出可用的软件，以及让开发者能独立解释设计、实现和取舍。**

固定主线：**需求 → 模块 → 数据 → 流程 → 并发与一致性 → 异常处理 → 扩展与验证**。

这条主线用于每个小功能；项目的七个交付阶段继续保留。每次选择一个可验证的小目标，按问题的复杂度决定分析深度，在实现和验证中修正设计。

项目范围与技术栈见 [README](../README.md)，已有架构取舍见 [ADR 0001](adr/0001-local-desktop-architecture.md)。本手册调整开发方法，不替换这些决策。

## 1. 默认协作方式

采用 **“你先设计，我追问评审”**：你是开发者，我是协作助手。

1. **给出任务**：我提供当前小目标、已确定的约束和最多三个引导问题，并补充回答所需的基础知识。
2. **你先提出方案**：你用文字、草图或伪代码表达思路；不确定的地方可以明确写出来，不需要先整理成完整技术文档。
3. **针对方案评审**：我先说明哪些部分成立，再针对缺口追问；每轮最多三个问题，优先处理会影响设计的部分。
4. **协助实现**：核心问题说清楚后，按你的需要协助实现。新的发现可以反过来修正设计卡，不要求预先穷尽所有细节。
5. **验证与复盘**：用运行结果和必要测试核对方案，再由你解释一次取舍与下一步改进。

提示逐级展开：先指出值得检查的场景，再提示相关概念，仍有困难时给局部示例。默认不在你提交初稿前附上完整设计、参考答案或整套代码。你明确要求示范或直接实现时，可以切换方式；已经确定的技术栈不必重新选择。

学习依附于当前功能。例如遇到持久化问题时补 SQLite 知识，遇到消息对应问题时补 IPC 知识，不要求先学完整套技术栈再开始。

## 2. 每个功能的七步推导

| 步骤 | 需要思考什么 | 最小产出 |
| --- | --- | --- |
| 需求 | 谁在什么场景下遇到问题？完成后有什么可观察的变化？ | 一个使用场景、成功标准、本次边界 |
| 模块 | 谁负责处理？谁不该知道这些细节？ | 职责划分与模块之间的输入输出 |
| 数据 | 哪些是事实，哪些是缓存？如何识别对象？谁负责写入？ | 必要字段、标识、归属及必须保持的规则 |
| 流程 | 从用户操作到完成，依次发生什么？什么时候可以显示成功？ | 正常流程或简短时序图 |
| 并发与一致性 | 重复点击、同时处理、旧结果晚到时，会不会产生矛盾？ | 相关竞争场景及一致性要求 |
| 异常处理 | 哪一步可能失败？失败后保留什么？能否重试？ | 关键失败状态与恢复方式 |
| 扩展与验证 | 如何证明正确？什么需求变化才值得调整设计？ | 验收例子、必要测试、重新评估条件 |

并发与异常从第一个功能开始思考。没有实际并发或扩展需求时，简要说明原因即可；不为填写模板增加锁、队列或抽象层。跨设备一致性、分布式锁和商业支付继续留在首版范围之外。

## 3. 一页设计卡

每个功能通常使用一张一页以内的设计卡，先写当前能说明的部分，评审和实现时继续补充。可以直接在讨论或工作笔记中使用；不为七步分别创建文件。普通实现问题留在设计卡或提交说明，重要架构取舍才另写 ADR。

下面是可复制的空白模板，不是已完成的练习：

```markdown
### 功能：<本次小目标>
状态：待设计 / 设计中 / 实现中 / 待验证 / 已完成

1. 需求：<场景、可观察的成功标准、本次边界>
2. 模块：<职责，以及彼此传递的输入输出>
3. 数据：<事实与缓存、必要字段、标识、归属和必须保持的规则>
4. 流程：<正常步骤，以及何时认定成功>
5. 并发与一致性：<相关场景、不能被破坏的规则；不涉及则说明原因>
6. 异常处理：<关键失败、保留状态、恢复或重试方式>
7. 扩展与验证：<验收例子、必要测试、重新评估条件>

实现后的证据：<演示结果、测试结果或尚未验证的部分>
复盘：<一种备选做法、当前取舍、下一步改进>
```

没有运行或验证过的结果保持待验证，不能因为设计卡填写完整就认定功能已完成。

## 4. 七个交付阶段与训练重点

下表是整段开发过程的训练地图，每阶段都重复七步推导；具体功能范围和工程验收仍与 README 对应。阶段 5 才接入真实 AI 调用。

| 阶段 | 交付内容 | 重点训练 |
| --- | --- | --- |
| 1. 最小桌面链路 | 选择一个视频 → 提取元数据 → 入库 → 展示，并验证打包运行 | 区分用户目标与技术步骤；理解模块边界、请求对应关系、持久化成功与界面成功的关系 |
| 2. 目录导入 | 批量索引、重复导入、文件变化与位置管理 | 区分文件路径和资产身份；分析重复操作、部分成功和旧结果失效 |
| 3. 浏览与搜索 | 缩略图、预览、标签、筛选及分页 | 区分事实数据与衍生缓存；分析快速切换筛选条件时的响应顺序 |
| 4. 后台任务 | 有界并发、任务状态、取消、恢复 | 设计状态转换；分析取消与完成同时发生、进程中断及数据库写入顺序 |
| 5. AI 整理 | 抽帧分析、人工修订、调用用量记录 | 区分本地任务与外部调用；分析超时但可能已执行、重复请求成本及人工修改冲突 |
| 6. 成本账本 | 费用计算、汇总、预算提醒和导出 | 推导记账规则、价格快照与金额精度；验证未知费用、重复结果和不同币种 |
| 7. 自用版本完善 | 备份恢复、缓存管理、素材重定位和规模验证 | 从真实故障与测量结果判断设计是否成立，并决定是否需要扩展 |

并发与一致性问题随交付逐步加深：阶段 1 先讨论重复操作和请求对应；目录导入时再分析文件变化与结果过期；阶段 4 系统建设任务调度、取消与恢复；AI 阶段再讨论外部调用的结果与费用。前面的分析不意味着必须提前实现后续所有机制。

## 5. 怎样判断一个功能完成

- **功能证据**：正常操作可演示，关键失败或重复操作有验证结果。
- **理解证据**：你能说明模块边界、数据归属，以及失败后为什么保留当前状态。
- **取舍证据**：你能说出一种备选做法、当前没采用的原因，以及何时值得重新考虑。

验证采用与改动相称的测试，优先覆盖会影响用户结果的行为，不为完成模板增加无关测试。代码能够运行、设计能够解释、结果能够验证，分别记录；某一项完成不替代另外两项。

每次复盘围绕本次功能的一次实际取舍展开，记录一个后续改进即可。尚未实现或尚未验证的项目继续标为待完成。

## 6. 第一个练习

### 目标

导入一个本地视频，并在关闭、重新启动应用后查看它的元数据。当前只展开设计入口，完整流程与异常策略在你提出初稿后逐步讨论。

### 已有约束

- 首发平台为 macOS Apple Silicon；本练习对应阶段 1，阶段交付需要验证打包后的应用能够运行。
- 已选择 Electron + React/TypeScript 与 Python worker，进程间使用 JSON Lines 通信。
- 业务数据存 SQLite，由 Python 业务层统一写入。
- 视频引用原位置，不搬走、不复制原文件；本练习不调用 AI，也不处理批量目录导入。

### 先回答三个问题

1. 从用户角度，怎样判断“导入完成”和“重启后仍可查看”已经实现？请描述可观察的结果。
2. 在已有架构中，你会让哪些模块参与，它们各自负责什么、彼此需要传递什么？
3. 为了重启后继续查看，你认为哪些信息必须持久保存，哪些可以临时保留或重新获得？
