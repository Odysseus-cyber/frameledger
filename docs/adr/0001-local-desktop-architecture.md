# ADR 0001：本地桌面应用的初始架构

- 记录日期：2026-11-12
- 状态：已采纳，尚未实施
- 适用范围：FrameLedger 的 macOS 单人自用首版
- 项目总览：[README](../../README.md)

## 背景

FrameLedger 由一人独立开发。开发者以 Python 为主要技术基础，同时希望软件具有 Web 风格的素材网格、详情面板和费用看板。首版优先服务 macOS Apple Silicon，管理不断增长的本地视频及外接硬盘素材。

这些条件同时影响界面、业务实现和存储方式：需要保留 Python 的开发优势，也需要学习并维护前端工程；视频体积较大，导入不应默认额外复制一份；单人使用的资产索引和 AI 成本记录应能在本机持久保存。

本文补充现有 README 中技术选型的理由、代价与重新评估条件。工程结构、开发阶段和费用计算规则继续以 README 为入口；本记录不表示已经完成打包或性能验证。

## 比较过的方案

下表是针对本项目需求与开发者基础的判断，不是对各框架的通用排名。

| 方案 | 对本项目的优势 | 主要代价 | 本次结论 |
| --- | --- | --- | --- |
| Electron + React/TypeScript + Python worker | 满足 Web 风格界面偏好，业务与 AI 逻辑继续使用熟悉的 Python | 两套依赖与构建、跨进程契约、进程退出和打包需要共同维护 | 采用；先验证最小安装包能独立运行 |
| Electron + React/TypeScript，业务也使用 TypeScript | 界面与业务统一语言，可省去 Python worker 的通信和分发 | 业务开发也要转向 TypeScript，减少对现有 Python 经验的直接复用 | 保留为后续简化方向；并非 AI 功能必须使用 Python |
| Python + PySide6 原生桌面 GUI | 界面与业务都可使用 Python，减少语言切换 | 需要学习 Qt 的界面体系，与当前明确选择的 React/Web 界面路线不同 | 本次不采用；技术上仍是可行选择 |

选择混合方案的依据是当前的开发经验和界面偏好，不预设它在性能、体积或开发速度上优于其他方案。

## 已采纳的决策

### 1. Electron 承载界面，Python 承担业务

React/TypeScript 负责展示与交互；Electron 主进程负责窗口、文件选择、本地媒体访问以及 worker 生命周期；一个常驻 Python worker 负责资产索引、媒体任务、AI 调用和成本账本。Python 是业务数据库的唯一写入方。

这样可以让 Python 业务模块独立于界面演进，同时把需要维护的业务实现集中在一处。AI 调用本身并不构成必须选择 Python 的理由，是否值得保留这一层要由后续实际开发价值判断。

### 2. 桌面应用与 worker 使用 JSON Lines 通信

当前只有桌面应用启动并使用该 worker，标准输入与输出已能承载请求、结果和任务进度。采用带请求 ID 的 UTF-8 JSON Lines，stdout 输出协议消息，stderr 输出日志；不为首版额外维护本地 HTTP 服务。

该选择仍需要处理消息分帧、并发请求对应关系、任务取消和进程异常。长视频通过文件路径引用，原始视频不经 JSON 消息传输。首版无需为尚未出现的浏览器或多客户端访问需求增加传输层。

### 3. SQLite 存放业务数据，视频保留原位置

SQLite 保存资产索引、标签、任务和费用等数据，视频留在用户选择的目录。缩略图和预览代理作为可重建缓存保存。对于当前单用户本地应用，这避免了运行独立数据库服务，也避免导入大量视频时默认复制素材的磁盘开销。

与“复制进软件管理的素材库”相比，原位索引更贴合现有目录和外接硬盘工作方式，但软件必须明确显示文件缺失、磁盘离线和需要重新定位的状态。数据库备份只覆盖索引及业务记录，不包含原视频。

## 接受的代价与验证方式

- **双语言维护**：前端和 Python 分别维护依赖、锁文件及构建流程；跨进程输入输出需要一致的契约和示例。
- **进程管理**：启动、异常退出、取消任务和关闭应用都需要正确处理 worker 及其 FFmpeg 子进程；不能只验证开发环境中的正常路径。
- **安装包复杂度**：需要一起分发 Electron、Python worker 的完整运行目录及媒体工具，并验证架构兼容、资源路径和必要签名。不预先承诺安装包大小或启动速度。
- **文件位置依赖**：用户移动目录或断开外接硬盘后，索引不会让文件自动恢复；需要重新定位，同时保留已有标签、来源和费用关联。
- **本地存储边界**：SQLite 的采用针对单机业务数据，不代表已经解决跨设备共享写入、团队协作或商业收款。

第一阶段的验证是：从 Finder 启动打包后的应用，启动 Python worker，读取一段视频的元数据并写入 SQLite，且不依赖开发目录、系统 Python 或 Homebrew。测试结果再用于判断当前混合架构的维护成本是否可接受。真实 AI 调用按 README 的阶段 5 接入。

## 何时重新评估

| 观察到的需求或问题 | 重新评估的方向 |
| --- | --- |
| 浏览器、CLI 或多个独立客户端确实需要访问业务服务 | 评估 HTTP 或其他服务接口，并重新划分服务生命周期；单个桌面进程内增加任务数量不自动触发迁移 |
| 出现跨设备共享数据、多个客户端并发写入或团队权限需求 | 评估服务端数据库及同步架构；不只根据视频数量决定替换 SQLite |
| Python 业务长期只是简单 API 转发，未体现经验或库复用收益，而跨语言维护成为持续负担 | 评估统一 TypeScript，减少 worker 与双重打包；结合实际维护记录决定 |
| 用户希望软件统一管理原文件，愿意承担复制和迁移的磁盘成本 | 评估增加托管素材模式，明确已有原位索引的迁移方式 |
| 打包验证显示当前依赖组合无法稳定独立运行，或实测资源开销影响使用 | 先定位依赖、构建与进程问题，再评估技术组合；不用未经测量的性能印象推翻架构 |

这些条件触发重新讨论，不代表达到条件后自动更换技术栈。后续若改变本决策，新增 ADR 并注明替代关系，保留当时的选择背景。

## 官方依据与项目判断

- [Electron 简介](https://www.electronjs.org/docs/latest/)说明 Electron 将 Chromium 与 Node.js 集成到桌面应用中。这支持 Web 技术构建桌面界面的可行性；选择它来匹配当前界面偏好，是本项目的判断。
- [SQLite 的适用场景](https://www.sqlite.org/whentouse.html)包含桌面应用与本地数据存储，也讨论客户端/服务端数据库更适合的场景。以它保存单人素材库的业务记录，是基于当前使用边界的选择。
- [PyInstaller 打包机制](https://pyinstaller.org/en/stable/operating-mode.html)说明可以将 Python 解释器及依赖打包分发，产物与构建平台有关。这支持独立分发 worker 的方案，但不等于 FrameLedger 已通过完整应用打包验证。
- [Qt Widgets 文档](https://doc.qt.io/qt-6/qtwidgets-index.html)说明 Qt 的桌面控件与界面体系。PySide6/Qt 是备选路线；本次不采用源于已确认的界面方向，而非认定其不能完成素材管理功能。
